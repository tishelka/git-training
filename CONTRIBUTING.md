# Как мы работаем вместе

Здесь собраны правила на случай, когда над одним репозиторием работают сразу восемь человек. Они нужны не ради бюрократии, а чтобы случайно не затереть чужую работу.

## Главное правило

**Одна задача — одна ветка — один Pull Request.** Не отправляйте учебные изменения сразу в `master`. Эта ветка — общая версия, которую мы стараемся держать аккуратной.

## Перед началом новой задачи

```bash
git switch master
git pull --ff-only origin master
git switch -c practice/yourname-task
```

Если `git switch master` не даёт переключиться из-за ваших правок, не удаляйте их наугад. Посмотрите `git status`; сохраните работу коммитом в своей ветке или спросите, как перенести её.

В названии ветки используйте латиницу и дефисы:
- `practice/anna-profile`
- `practice/max-readme`
- `fix/typo-in-guide`

## Как делать коммиты

Хорошие примеры:
- `Add Anna profile`
- `Fix broken link in README`
- `Update team list`

Не очень: `123`, `final-final` и `changes`. Через неделю никто не вспомнит, что именно менялось.

## Как оформлять PR

1. Дайте PR короткое, понятное название.
2. Напишите, что сделали и как проверяли.
3. Посмотрите вкладку **Files changed**: нет ли случайных файлов?
4. Дождитесь проверки, ответьте на замечания и внесите правки в ту же ветку.
5. Не закрывайте замечания молча, если не понимаете, что требуется.

**Важно:** изменения в PR появятся автоматически после новых коммитов и `git push` в ту же ветку. Второй PR для исправления первого не нужен.

## Как не мешать друг другу

Пока выполняем первое задание, каждый редактирует **только свой файл** `students/ник.md`. Не меняйте `README.md` и файлы одногруппников без отдельного задания.

Перед отправкой полезно выполнить:

```bash
git status
git diff --check
git diff --cached
```

Последняя команда показывает, что именно попадёт в коммит после `git add`.

Не добавляйте пароли, токены, ключи API, личные адреса или другие секреты. Не коммитьте случайно папки `node_modules` и `.env`.

## Кто объединяет изменения

Учебные PR просматривает руководитель. Он же решает, когда объединять изменения с `master`. Если у вас есть право слияния, всё равно дождитесь ревью.

После merge начните следующую задачу от свежей `master`, а не от старой рабочей ветки.
